# 2026-03-29 中期记忆与画像改造 PR 说明

## 1. 改动背景

本次改动是在已有“第一层短期记忆（Redis Token 滑动窗口）”的基础上，继续落地“第二层中期记忆”。

核心问题是：

1. 仅靠 Redis 的短期窗口，老对话虽然不再进入 Prompt，但其中仍然包含用户偏好、约束条件、已解决问题等高价值信息。
2. 如果把所有历史永久原文带给模型，成本高、时延高、上下文还容易爆掉。
3. 在多实例和 Redis/数据库双写场景下，摘要和画像也必须遵守“数据库为真源、Redis 为缓存副本”的一致性原则。

因此，这次改造的目标是：

- 当单个 session 的对话累积到一定规模后，自动异步摘要压缩。
- 把摘要分成两层：
  - session 级中期记忆摘要
  - user 级主体画像摘要
- 让主聊天链路在组装 Prompt 时，自动把这两类高浓度上下文作为 `SystemMessage` 注入。

---

## 2. 设计原则

### 2.1 两层记忆分工

- **第一层：短期记忆**
  - 存在 Redis List 中
  - 保存最近原始对话
  - 使用 Token 预算动态截断
  - 目标是保留最近连续上下文

- **第二层：中期记忆**
  - 基于历史对话做摘要压缩
  - 保存高浓度信息，不再保留全部原文
  - 用于在长会话中持续携带偏好、约束、已解决事项

### 2.2 一致性原则

- PostgreSQL 是最终真源
- Redis 是派生缓存，不承担唯一事实来源角色
- 摘要与画像采用：
  - **先写数据库**
  - **后写 Redis**
- Redis 丢失后允许：
  - **数据库回源**
  - **回填 Redis**

### 2.3 分布式原则

- 对 session 摘要与 user 画像生成都加了 Redis 分布式锁
- 避免多实例并发重复压缩、互相覆盖
- 避免重复调用小模型造成成本浪费

## 3. 主要改动点

## 3.1 新增中期记忆服务

新增文件：

- `src/main/java/com/honghu/ut/test/ai/assigment/testdeepseekr1/service/ChatSummaryService.java`
- `src/main/java/com/honghu/ut/test/ai/assigment/testdeepseekr1/service/MemorySummaryClient.java`
- `src/main/java/com/honghu/ut/test/ai/assigment/testdeepseekr1/service/SpringAiMemorySummaryClient.java`

### 作用

`ChatSummaryService` 负责：

1. 判断 session 是否达到摘要阈值
2. 对 session 历史做压缩
3. 聚合最近 10 个 session，生成 user 主体画像
4. 把结果先保存数据库，再写入 Redis 缓存
5. 给 `ChatService` 提供可直接注入 Prompt 的 `SystemMessage` 文本

`MemorySummaryClient` 是模型调用抽象层，用来把“摘要业务逻辑”和“调用 Spring AI/Ollama”解耦。

`SpringAiMemorySummaryClient` 则是具体实现。

---

## 3.2 在 ChatService 中接入中期记忆

修改文件：

- `src/main/java/com/honghu/ut/test/ai/assigment/testdeepseekr1/service/ChatService.java`

### 改动内容

在组装 Prompt 时新增两类中期上下文：

1. 用户最近十个 session 聚合出的主体画像
2. 当前 session 的中期记忆摘要

并且在计算短期历史消息 Token 预算时，已经把这两部分 SystemMessage 的 Token 成本一起扣除了。

### 为什么这么做

如果只把摘要塞进 Prompt，但不参与预算计算，就会出现：

- 历史消息截断不准确
- Prompt 总长度超预算
- 模型上下文膨胀

所以必须把“默认系统提示词 + 用户主体画像 + session 摘要 + 短期历史”统一纳入预算控制。

### 新增表

#### `chat_session_profile`

用途：保存单个 session 的中期摘要。

关键字段：

- `session_id`
- `user_id`
- `profile_summary`
- `last_summarized_chat_id`
- `summarized_message_count`
- `summary_model`

#### `user_profile_snapshot`

用途：保存用户最近 10 个 session 聚合出的主体画像。

关键字段：

- `user_id`
- `profile_summary`
- `source_session_count`
- `source_session_ids`
- `summary_model`

### 为什么拆成两张表

因为两类数据的生命周期和使用场景不同：

- session 画像更偏局部上下文
- user 画像更偏稳定长期偏好

如果混在同一张表中，后续维护、增量更新和索引设计都会更混乱。

## 4. 本次 review 发现并修复的问题

## 4.1 `@Async` 开关实际上不生效

### 问题

原实现中 `triggerRefreshSessionSummaryAsync()` 直接标了 `@Async`，即使代码里判断了 `summaryAsyncEnabled=false`，方法也已经被 Spring 异步代理拦截了，实际上还是异步执行。

### 修复

改为：

- 不再依赖 `@Async`
- 直接注入 `memorySummaryTaskExecutor`
- 在方法内部根据配置决定：
  - 同步执行
  - 或提交到线程池异步执行

### 收益

配置开关语义与实际行为一致。

---

## 4.2 一次请求会触发两次摘要压缩

### 问题

原先在：

1. 用户消息落库后
2. assistant 消息落库后

都触发了一次摘要刷新。

这会导致：

- 重复抢锁
- 重复查询历史
- 重复调用小模型
- 造成不必要成本

### 修复

保留在 assistant 完整落库后的触发点。

### 原因

assistant 回复完整后再做压缩，更符合“完成一轮对话后再沉淀中期记忆”的语义。

---

## 4.3 session 摘要未变时仍重复刷新用户画像

### 问题

如果 session 摘要已经覆盖到最新消息，但每次请求仍继续刷新 user 主体画像，会导致最近 10 个 session 再次被聚合，增加模型消耗。

### 修复

当检测到 session 摘要已是最新时，仅做 session Redis 缓存自愈，不再重复刷新用户画像。

### 收益

- 减少重复模型调用
- 降低热点用户下的聚合开销
- 降低多实例环境中的锁竞争

---

## 4.4 仓储返回不可变列表时排序报错

### 问题

测试里使用 `List.of(...)` 模拟仓储返回，`resolveMessagesToSummarize()` 里直接 `sort()` 会触发 `UnsupportedOperationException`。

### 修复

先复制为 `new ArrayList<>(messages)` 再排序。

### 收益

代码对真实仓储返回和测试桩返回都更健壮。

## 6. 当前实现的优点

1. 结构清晰：短期记忆、中期记忆、用户画像分层明确
2. 一致性明确：数据库真源，Redis 缓存副本
3. 性能可控：短期历史按 Token 截断，摘要异步执行
4. 分布式可用：摘要与画像刷新都有锁保护
5. 可调优：线程池和摘要参数都已配置化
6. 可测试：已经补了摘要服务单测与路由测试

## 7. 当前实现的边界与后续建议

### 7.1 当前边界

- 还没有做“定时补偿扫描”，目前主要依赖主链路触发摘要刷新
- 用户主体画像是否需要做“摘要内容指纹去重”还未实现
- Prompt 中目前是直接拼文本摘要，而不是结构化 JSON 画像

### 7.2 后续建议

1. 增加一个定时补偿任务，扫描达到阈值但尚未生成摘要的 session
2. 给 session/user 画像增加摘要版本号或内容哈希，进一步减少重复聚合
3. 如果后续要做人设/偏好检索，可以把摘要拆成结构化字段

## 9. 结论

这次改动的本质，是把项目的记忆体系从“只有短期窗口”升级为：

- **短期原文窗口**：保留最近连续上下文
- **中期摘要记忆**：保留当前会话的压缩高浓度信息
- **长期用户画像**：保留最近十个 session 的稳定偏好与背景

这样做的核心收益是：

- 更省 token
- 更强上下文延续性
- 更适合长会话和多 session 用户
- 更符合分布式系统下“数据库真源 + Redis 派生缓存”的工程实践
